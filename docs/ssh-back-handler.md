# The ssh-back handler: clicking over SSH without per-session forwards

*Design, not implementation. What exists today is the manual recipe: over SSH,
`/snippets` → "Remote clicking" paints chip URLs again and prints the `ssh -L`
argument that carries this session's socket across the wire. It works, and it
costs a flag on every ssh invocation and a session resume. This document
designates the successor: register the handler on the **client** machine, and
let a click that finds no local socket relay itself back over SSH to the host
the session lives on.*

## The inversion, stated precisely

Everything before the socket already happens on the client:

1. the remote pi paints `pisnip://<token>/<msg>/cN` into an OSC 8 hyperlink;
2. the bytes travel over SSH as ordinary output;
3. the local terminal underlines the chip and resolves Ctrl+click;
4. the local desktop opens the URL.

Only the last hop is inverted: the desktop hands the URL to a handler on the
client, and the handler looks for a unix socket named `<token>.sock` in
directories that, over SSH, hold nothing. The socket lives on the remote host,
inside (or beside) the pi process.

So the question is never "how does a click become a message" — that machinery
exists on both ends, unmodified. It is "how does the click cross the wire
backwards". Two answers exist. The manual forward tunnels the socket through
the user's own ssh command (shipped). This document tunnels the *click*
through a fresh ssh invocation instead.

## The shape

The handler gains one branch, after its local socket scan fails:

```python
host = config.default_remote()          # never taken from the URL
if host is None:
    explain_once()                      # notify-send, rate-limited
    sys.exit(1)
subprocess.run(
    ["ssh", "-o", "BatchMode=yes", "-o", "ConnectTimeout=3", host,
     REMOTE_ONE_LINER, url],
    timeout=10,
)
```

`REMOTE_ONE_LINER` is a fixed, self-contained python3 command that walks the
same ordered socket-directory candidates the local handler does — the
handler/link-server agreement (`socketDirCandidates()` ↔ the handler's
`candidates()`) now spans three processes on two machines, and must stay a
single list in three places, or the relay silently misses. It connects to
`<token>.sock`, writes the URL path as one line, and exits. From there the
existing path takes over: the extension resolves the key against its link
targets and inserts into the composer.

No remote-side install is required. `python3` and `ssh` are both near-universal
on the hosts this feature targets, and the one-liner is generated by the same
`handlerSource()` that generates the handler, so the two cannot drift apart
silently — a regeneration updates both.

## What the client needs, once

1. The handler registered: same pi, same `/snippets` → *Register click
   handler*. The handler is stateless today and stays so; the branch above is
   generated into it like the rest.
2. A relay host on file: `~/.pi/agent/pi-snippet-remotes.json`, written by the
   local pi's `/snippets` → *Configure SSH relay host*. One field in v1:
   `{ "host": "mybox" }` — an ssh-config alias resolves through the user's own
   `~/.ssh/config`, so keys, ports, and jump hosts are already the user's
   problem, solved the way they already solve them.
3. `mkdir -p /tmp/pi-snippet-$(id -u)` — or any directory the handler scans.
   The registration flow can do this; it is the same directory the handler
   would use locally anyway.

The bootstrap is in-band, because the remote pi cannot touch the client
desktop: the remote `/snippets` → *Remote clicking* entry puts the command to
run on the client into the composer (the editor, not a toast — toasts clip at
the terminal width and coalesce within a render tick, both measured live).
One copy-paste, once per client machine — not per session, which is the
entire point.

## Failure semantics

The handler's silence is a feature today: a chip clicked in old scrollback
finds no live session and exits 1 quietly, because an error dialog for a
perfectly dead chip is noise. Over SSH, a *new* failure state appears that is
not that: the socket is alive, the session is live, and the click died for a
reason the user can fix. The handler must distinguish:

- **Unconfigured.** The one state worth telling the user about, because it has
  a one-time fix. `notify-send` (when present) with the instruction, rate-
  limited through a stamp file in the runtime directory — one notification per
  token per hour, say, since the handler is stateless and spawns fresh per
  click. A handler with no display and no `notify-send` degrades to the old
  silence.
- **Configured, relay failed.** BatchMode refused, connect timed out, no
  socket at the far end. Quiet exit 1 — a dead or suspended session is the
  same situation as dead scrollback, and the user has already opted in; there
  is nothing to configure.
- **Configured, relay succeeded, nothing resolved.** The remote session says
  nothing back (the socket protocol is fire-and-forget by design). Same as
  local: the click inserted, or referred to a message that moved on. Silence.

## Security

The click path crosses a trust boundary it never had to cross before — a URL
that arrived from a remote machine now causes *this* machine to open an SSH
connection. Four rules keep that boring:

1. **The host never comes from the URL.** A chip URL is render-time state —
   built by the extension from the session id, never from model text — and
   this design must not erode that invariant. A hostname in the URL would make
   any pasteable `pisnip://` link an instruction to SSH somewhere; the config
   file is the allowlist. If per-host disambiguation is ever needed, it is a
   key *into* the config, never a host literal.
2. **Fixed argv end to end.** The handler execs `ssh` with the URL as one
   argument; nothing is shell-interpolated. One subtlety: `ssh host cmd arg`
   hands `cmd arg` to the *remote* shell as a single command line, so the URL
   is re-parsed by a shell after all. This is safe only because the URL's
   shape is validated strictly — netloc `isalnum()`, path matching
   `^/[0-9a-f]{8}/c\d+$` — before the branch runs, so the remote shell has no
   metacharacter to act on. The validation is the security boundary, not the
   argv split; both are load-bearing.
3. **`BatchMode=yes`.** A click must never hang on a password prompt or an
   interactive host-key confirmation. BatchMode makes any credential problem
   fail fast and visibly (in the relay-failure sense above) instead of
   stacking invisible ssh processes.
4. **`ConnectTimeout`, and a subprocess timeout.** A dark host costs seconds,
   not minutes, and never outlives the click.

What the remote one-liner can do even if the URL lies: connect to a unix
socket whose name the URL selects, and write the URL path as one line. It
cannot start a shell, read a file, or address any other process — the token
only ever names a pi-snippet socket, and the receiving extension validates the
key against its own link targets before inserting anything. The worst a
forged URL achieves is text insertion into a live composer — which the
session-token scheme already prevents for foreign sessions, and which the
model could achieve anyway by simply writing the text.

## Latency

Without connection multiplexing, each click pays an SSH handshake — a couple
hundred milliseconds on a good link, seconds on a bad one. That is tolerable
for an event as rare as a chip click, but `ControlMaster`/`ControlPersist`
collapses it to the socket write. The remote `/snippets` recipe should say so
in one line rather than trying to configure it (touching the user's ssh
config is out of bounds for an extension).

## What it replaces, and what it doesn't

The manual `ssh -L` forward stays. It needs no client config file, works
today, and suits a user who wants the tunnel visible in their own ssh
invocation. The relay replaces its *per-session* cost — no flag, no resume
dance, no token in the command line — with a one-time per-client setup. Both
paths feed the same socket protocol, the same verify window in `/snippets`,
and the same Alt+N fallback underneath.

## Testing

The harness pattern extends one hop: sshd on localhost, the tmux harness
driving real pi through a real pty, the click asserted end to end — local
handler invocation, relay, remote socket, insertion. The failure paths are
asserted too: BatchMode against a deliberately unauthenticated account must
produce the quiet exit, and an unconfigured client must produce the
rate-limited `notify-send` (asserted by stamp file, not by scraping desktop
notifications).

## Open questions

- **macOS clients.** The handler is Linux-only (`xdg-open`, mimeapps.list);
  an macOS client needs its own dispatch (Launch Services + a stub app).
  Out of scope here, but the config file and relay protocol should not
  assume Linux on the *client* beyond the handler itself.
- **Multiple simultaneous remotes.** One default host covers the ordinary
  case. Per-token overrides in the config map are the escape hatch; whether
  they are ever worth UI is deferred until someone needs them.
- **Learning the mapping.** The remote pi knows which host it is on
  (`SSH_CONNECTION`) and could print it for the config; it cannot write the
  client's config. Keep it that way.
