# The ssh-back handler: clicking over SSH with nothing to set up

*Shipped, and the only way a click crosses the wire. Register the handler on
the **client** machine once — that is the whole of it. A click that finds no
local socket reads the host out of the URL and relays itself back over SSH to
the session that painted it: no forward, no flag, no config file, no toggle,
nothing per session.*

*Two things this document was written beside have since been removed, and both
are worth knowing about because their absence is load-bearing. The `ssh -L`
forward went first (see "What it replaced"). Then ADR 0001 —
`docs/adr/0001-the-chip-url-names-its-server.md` — put the server's own name in
the chip URL and took the client-side host list, the walk, the cache, the
server-side stamp and the bootstrap line with it. Where this document said
"never from the URL", read the ADR: it reverses that rule deliberately and says
what replaced it.*

## The inversion, stated precisely

Everything before the socket already happens on the client:

1. the remote pi paints `pisnip://<host>/<token>/<msg>/cN` into an OSC 8
   hyperlink, where `<host>` is what the server calls itself;
2. the bytes travel over SSH as ordinary output;
3. the local terminal underlines the chip and resolves Ctrl+click;
4. the local desktop opens the URL.

Only the last hop is inverted: the desktop hands the URL to a handler on the
client, and the handler looks for a unix socket named `<token>.sock` in
directories that, over SSH, hold nothing. The socket lives on the remote host,
inside the pi process.

So the question is never "how does a click become a message" — that machinery
exists on both ends, unmodified. It is "how does the click cross the wire
backwards". This tunnels the *click* through a fresh ssh invocation.

## The shape

The handler gains one branch, after its local socket scan fails:

```python
host = u.netloc                          # the server named itself
if is_this_machine(host):
    sys.exit(1)                          # a dead local chip, not a trip
subprocess.run(
    ["ssh", "-o", "BatchMode=yes", "-o", "ConnectTimeout=3", "--", host,
     REMOTE_ONE_LINER, url],
    timeout=10,
)
```

`REMOTE_ONE_LINER` is a fixed, self-contained python3 command that walks the
same ordered socket-directory candidates the local handler does — the
handler/link-server agreement (`socketDirCandidates()` ↔ the handler's
`candidates()`) spans three processes on two machines, and must stay a single
list in three places, or the relay silently misses. It connects to
`<token>.sock`, writes the message key and chip id as one line, and exits. From
there the existing path takes over: the extension resolves the key against its
link targets and inserts into the composer.

No remote-side install is required. `python3` and `ssh` are both near-universal
on the hosts this feature targets, and the one-liner is generated by the same
module that generates the handler, from one `PY_CANDIDATES` string, so the two
cannot drift apart silently — a regeneration updates both.

The self-check exists because there is one URL shape everywhere: a local
session names its own host too. Without it, a click on scrollback whose session
has exited would ssh to this very machine to fail a second time, slower. Names
are compared on the first label, case-insensitively, and `localhost` always
means us.

## What the client needs, once

The handler registered: `/snippets` → *Register click handler*, on the machine
the desktop is on. That is the list. There is no relay config, no directory to
create (the handler falls through a missing candidate like any other miss), and
nothing to run on the server.

What the *server* may occasionally need is one string: `PI_SNIPPET_HOST`, when
`hostname` is not a name the client can dial (`ip-10-0-3-14`, a container id, a
name that only resolves inside a VPC). It is the escape hatch for the one
assumption this design rests on, and it lives on the machine that knows the
answer rather than in a file on every client.

## Failure semantics

The handler's silence is a feature: a chip clicked in old scrollback finds no
live session and exits 1 quietly, because an error dialog for a perfectly dead
chip is noise. Every remote failure now collapses into the same silence, which
is a deliberate trade the ADR records as a cost:

- **The named host is this machine.** Nothing local answered and there is
  nowhere else to look. Exit 1.
- **Relay failed.** BatchMode refused, the host is not in `known_hosts`, the
  connect timed out, or no socket answered at the far end. The relay's own exit
  status is passed straight out. A dead or suspended session is the same
  situation as dead scrollback, and there is no longer anything to configure —
  so there is nothing to say either. (The rate-limited `notify-send` that used
  to explain an unconfigured client went with the config file: it had exactly
  one job, and that state no longer exists.)
- **Relay succeeded, nothing resolved.** The remote session says nothing back
  (the socket protocol is fire-and-forget by design). Same as local: the click
  inserted, or referred to a message that has moved on. Silence.

## Security

The click path crosses a trust boundary it never had to cross before — a URL
that arrived from a remote machine causes *this* machine to open an SSH
connection. Since ADR 0001 the host in that URL is the destination, so the
rules that keep it boring have changed shape:

1. **`known_hosts` is the allowlist.** The relay runs `BatchMode=yes`, which
   turns `StrictHostKeyChecking`'s "ask" into a hard failure, so a host that is
   not already in `known_hosts` is refused at the host-key check — before
   authentication, before the agent is ever offered. The reachable set is
   "machines this user has connected to before", maintained by ssh rather than
   by us. This is what replaced the config file that used to be the allowlist,
   and it is the whole of the argument: the container harness asserts it by
   pointing a URL at the same sshd under a second DNS name and requiring no
   delivery.
2. **The host's shape is a guard, not a formality, and `--` backs it up.**
   `^[A-Za-z0-9][A-Za-z0-9._@-]{0,254}$` — `isLinkHost()` in
   `shared/link-url.ts` and the same pattern written out in the handler. The
   leading class is narrower than the rest on purpose: `ssh … -Jevil.com cmd
   url` makes ssh read the host slot as an option and shift the destination to
   the next argument. That was harmless while only the user could write the
   string and is not once it comes from a URL. `--` before the host is the
   second guard for the same hazard.
3. **Fixed argv end to end.** The handler execs `ssh` with the URL as one
   argument; nothing is shell-interpolated. One subtlety: `ssh host cmd arg`
   hands `cmd arg` to the *remote* shell as a single command line, so the URL
   is re-parsed by a shell after all. This is safe only because the URL's shape
   is validated strictly — the host pattern above, and a path matching
   `^/[0-9a-z]{1,32}/[0-9a-f]{1,16}/c[0-9]{1,3}$` — before the branch runs, so
   the remote shell has no metacharacter to act on. The validation is the
   security boundary, not the argv split; both are load-bearing. The path
   pattern matches `parseChipPath()` in `shared/link-url.ts` with the session
   token in front, rather than tightening past it: a handler that rejects a URL
   the extension would have accepted is a click that dies for no reason the
   user can see. The relay one-liner is embedded in a single-quoted shell word
   and therefore must contain no apostrophe — a test asserts that, because the
   failure mode is handing python's source to a shell.
4. **`BatchMode=yes`.** A click must never hang on a password prompt or an
   interactive host-key confirmation. BatchMode makes any credential problem
   fail fast instead of stacking invisible ssh processes — and, per (1), is
   what makes an unknown host a refusal rather than a question.
5. **`ConnectTimeout`, and a subprocess timeout.** A dark host costs seconds,
   not minutes, and never outlives the click.

What the remote one-liner can do even if the URL lies: connect to a unix socket
whose name the URL selects, and write the path as one line. It cannot start a
shell, read a file, or address any other process — the token only ever names a
pi-snippet socket, and the receiving extension validates the key against its
own link targets before inserting anything. The worst a forged URL achieves is
text insertion into a live composer, on a machine the user has already
connected to — which the session-token scheme already prevents for foreign
sessions, and which the model could achieve anyway by simply writing the text.

## Latency

Without connection multiplexing, each click pays an SSH handshake — a couple
hundred milliseconds on a good link, seconds on a bad one. That is tolerable
for an event as rare as a chip click, but `ControlMaster`/`ControlPersist`
collapses it to the socket write. Touching the user's ssh config is out of
bounds for an extension, so this is a note rather than a feature.

## What it replaced

**The manual `ssh -L` forward** was kept beside this at first — it needed no
client config, it worked, and it suited a user who wanted the tunnel visible in
their own ssh invocation. Both paths always fed the same socket protocol from
the same pair of machines; the forward's price was per session (a flag on every
connection, a resume after every reconnect, a socket named by a token that dies
with the process). Two things went with it, and neither is coming back on its
own:

- A client that can only ssh back **interactively** — a password-only login —
  has no way in, because the relay runs `BatchMode=yes` precisely so a click
  can never hang on a prompt. A key or an agent-forwarded identity is a
  requirement, not a convenience.
- Anyone who preferred the tunnel visible in their own command line has no such
  option; what the relay does is visible in the handler and in this document
  instead.

**The client host list, and everything that supported it.** A file the user
wrote (`pi-snippet-remotes.json`), a walk through it with the answering host
cached per token, a stamp directory on the server recording which clients had
set the relay up, the gate in the extension that read it, and a two-part
bootstrap line pasted once per client machine to create the first two. All four
existed to answer one question the server already knew the answer to — *which
machine is this session on* — so ADR 0001 had the server say it in the URL and
deleted them. What that bought: no setup beyond the handler, one ssh instead of
up to N, and one URL shape with one parser story. What it cost: a click that
cannot be delivered is silent in one more way, and the server can no longer say
honestly whether clicking will work, because it paints URLs unconditionally and
finds out never.

`Alt+N` is unaffected and remains the in-band path that needs no wire at all.

## Testing

**Two containers, not localhost** — `scripts/docker-ssh-env.sh` builds them,
`scripts/ssh-click-docker.py` drives them — because a relay to `localhost` can
pass while the click never leaves the machine, and the whole feature is the
wire. `ssh-relay-client.py` removes the local socket directory before it
clicks, so nothing there can answer by accident, and the flow it asserts is now
the whole feature with no setup phase in it: start pi over SSH, send a message,
the chip carries a URL naming the server, click it on the client, the text
lands in the remote composer. Then again after a restart, since there is no
per-session state left anywhere and that is worth proving.

Two negative cases carry the security argument, because the guards above *are*
the argument:

- A URL naming `otherserver` — the same sshd, the same key, a second DNS name
  the client has never connected to — must deliver nothing. It fails at ssh's
  host-key check, which is what "known_hosts is the allowlist" means in
  practice.
- A host with a leading `-`, or a space, or a `;`, must be refused before a
  process is spawned at all (exit 2, not 1).

`test/ssh-relay.test.ts` covers what does not need two machines by *running*
the generated handler with a recording `ssh` stub on its PATH: the local socket
still wins over the relay, the relay argv carries `BatchMode=yes`, the timeout
and `--` immediately before the host, a URL for this machine never reaches
`ssh`, a malformed URL or a hostile host exits before anything shells out, and
a relay failure is a quiet non-zero. Those tests skip where python3 is absent
rather than passing silently — `npm test` may not assume an interpreter it does
not install. The remote half is run the same way: the relay one-liner against a
live socket, including the shapes it refuses on its own.

## Open questions

- **macOS and Windows clients.** The handler is Linux-only (`xdg-open`,
  mimeapps.list); a macOS client needs its own dispatch (Launch Services + a
  stub app). Out of scope here — but the relay protocol assumes nothing about
  the client beyond `ssh` and `python3`, and the URL shape assumes nothing at
  all, which is one thing less for a second platform to reimplement.
- **Hosts not reachable by name.** The assumption ADR 0001 records, with
  `PI_SNIPPET_HOST` as its escape hatch. If it ever fails in a way one string
  cannot fix, the ADR names the fallback: the server's host-key fingerprint as
  a selector into the client's own `known_hosts`, which selects among machines
  the client already knows rather than naming one.
